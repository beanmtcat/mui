# 中转质量判断与手动干预（设计）

目标：链路里同一跳有多个中转时，自动避开"连得上但很卡、或后面已经断了"的中转；管理员也能手动把某个中转设为正常、降级或故障。

本文分两个阶段，一次只做一个：

1. 阶段 A：手动干预与状态展示（面板 + Agent）
2. 阶段 B：自动质量判断（Agent，面板只展示）

先做手动，是因为它简单、可控，遇到攻击时马上能用；自动判断的状态机也要建立在阶段 A 的三档状态之上。

通用约束：

- 不提交、不推送；每个阶段结束时按文末"汇报格式"汇报。
- 每个阶段结束时 `go build ./...`、`go vet ./...`、`go test ./...`、`web` 下 `npx tsc --noEmit` 与 `npm run build` 全部通过。
- 数据库同时支持 SQLite 与 PostgreSQL；新表、新索引走 `internal/server/store_migrate.go` 追加迁移。
- Agent 版本号升到 **0.6.32**（0.6.31 已发布），两个阶段共用这一个版本；只改版本号和 `docs/releases/v0.6.32.md`，**不构建、不发布**。
- 新代码放新文件，不要把已有文件写回到上千行。

## 现状（实现前请先读）

- 转发由上一跳服务器上的 `mui-forward` 执行：`internal/forward/`。
  - `forward.go`：`healthInterval = 5s`、`healthTimeout = 3s`、`healthStreak = 2`；`probe` 只做 TCP 建连，不记录耗时；`Reload` 对端点没变的规则保留运行中的连接（`sameEndpoints`）。
  - `target.go`：每个目标只有 `down` 一个布尔状态；`observe` 连续 2 次一致就翻转；`markDownFor` 用于实际转发失败。
  - `rule.go`：`candidates()` 健康的在前、故障的在后兜底；轮询模式在健康目标里轮转；状态变化时 `rebalanceSessions` 关掉不该用的 UDP 会话。
  - `tcp.go`：`dialUpstream` 按候选顺序依次尝试，失败立刻 `failedTarget`；`tcpPair.transferred` 记录连接是否传过数据。
- 面板把链路展开成转发规则：`internal/server/route_forwards.go` 的 `routeForwards`。`shared.ForwardTarget` 目前只有 `host`、`port`。
- 链路延迟：Agent `internal/agent/route_latency.go` 单独测 TCP 建连耗时，经 `/agent/report` 的 `routeLatencies` 上报，面板 `internal/server/route_latency.go` 校验后展示。目前只用于显示。
- 一跳 = 一组服务器（`shared.RouteHop.ServerIDs`），`Balance` 为 `failover` 或 `round-robin`。

## 三档状态

| 状态 | 新连接 / 新 UDP 会话 | 现有 TCP 连接 | 现有 UDP 会话 |
| --- | --- | --- | --- |
| 正常 | 正常分配 | 保持 | 保持 |
| 降级 | 排在所有正常目标之后，只在没有正常目标可用时使用；轮询模式下不参与轮转 | 保持 | 保持 |
| 故障 | 自动判定的故障：排在最后兜底（与现在相同）；**手动故障：完全不用，连兜底也不用** | 保持 | 按现有逻辑迁走 |

候选顺序：正常（按原规则排序或轮转）→ 降级（按配置顺序）→ 自动故障（按配置顺序）。手动故障不在候选里。

## 阶段 A：手动干预与状态展示

### A.1 作用范围

手动状态有两个层级：

- **服务器级**：这台服务器在所有链路里作为下一跳时的状态。例如"日本 B 被打了，全部降级"。
- **线路级**：某一条"上一跳服务器 → 这台服务器"的状态。例如"只有上海 1 到日本 B 很差"。

线路级优先于服务器级。只针对链路生成的转发（`RouteID` 非空，或共享监听里来自链路的目标）；手动创建的普通转发不在本阶段范围内。

每条手动设置包含：

| 字段 | 说明 |
| --- | --- |
| `state` | `normal`（强制正常）、`degraded`（强制降级）、`down`（强制故障） |
| `until` | 可选的到期时间；到期后自动回到"自动"。前端提供 1 小时、6 小时、24 小时、7 天、永久 |
| `note` | 可选备注，最多 200 个字符 |

"强制正常"的含义：**覆盖服务器级的手动设置，并且不让阶段 B 的自动"降级"生效**；但**自动"故障"照常生效**（连续 2 次探测失败或真实连接建连失败后，排到所有可用目标之后兜底）。否则一台已经连不上、又被强制正常的首选中转，会让每个新连接都先等它超时（被丢包时每次约 5 秒）。

### A.2 存储与接口

新表（新迁移）：

```
mui_relay_overrides(
  from_server_id TEXT NOT NULL,   -- 服务器级用空字符串
  to_server_id   TEXT NOT NULL,
  state          TEXT NOT NULL,   -- normal | degraded | down
  until_ms       BIGINT NOT NULL, -- 0 = 永久
  note           TEXT NOT NULL,
  updated_ms     BIGINT NOT NULL,
  PRIMARY KEY(from_server_id, to_server_id)
)
```

接口（都挂 `a.require`，写审计 `relay.override.set` / `relay.override.clear`）：

- `GET /api/relay-overrides`
- `PUT /api/relay-overrides`：`{fromServerId, toServerId, state, until, note}`，`fromServerId` 为空表示服务器级。
- `DELETE /api/relay-overrides?from=&to=`：回到自动。

校验：

- 两个服务器 ID 都必须存在；线路级要求这条线路确实出现在某条启用的链路里。
- **不能让任何一跳没有可用目标**：设置 `down` 前，对每条受影响的链路检查该跳在这条上一跳视角下是否还剩至少一个非手动故障的目标；不满足时返回 400，并列出受影响的链路名。单服务器的一跳不允许设为 `down`（提示改为停用链路）。
- 删除服务器时清理相关行；到期的行由面板定时清理（每分钟），清理后触发下发。

### A.3 下发到 Agent

- `shared.ForwardTarget` 增加：`serverId`（面板生成链路转发时填，用于上报对应）和 `override`（`""`、`normal`、`degraded`、`down`）、`overrideUntil`（时间，可空）。普通手动转发不填。
- 面板生成链路转发时，按"线路级 > 服务器级 > 无"给每个目标填上 `override`。
- 设置或清除后，只给受影响的上一跳服务器排队下发，走现有的签名下发流程。
- **改变 `override` 不能重启规则**：`sameEndpoints`（及类似的比较）要忽略 `override` / `overrideUntil` / `serverId`，运行中的规则就地更新这几个字段，已有 TCP 连接保持；状态变化后按 A 节表格处理 UDP 会话。补测试：改 override 后已有连接不断。
- Agent 端也检查 `overrideUntil`，到期后按"无手动设置"处理（面板不可达时也能按时恢复）；时间判断留 1 分钟余量。
- 旧 Agent 会忽略新字段，相当于没有手动设置；面板对旧 Agent 的服务器在界面上提示"需升级到 0.6.32 才生效"。

### A.4 状态上报

`/agent/report` 增加 `relayStates`（最多 200 条）：

```
{forwardId, serverId, host, port, state, source, autoState, reason, since}
```

- `state`：实际生效的状态。
- `source`：`manual` 或 `auto`。
- `autoState`：自动判断的结果；阶段 A 只有 `normal` / `down` 两种（沿用现有健康检查），阶段 B 加入 `degraded`。被手动覆盖时也照常上报，让管理员能看到"手动设为正常，但自动判断为故障"。
- `reason`：固定枚举，不带任意文本（例如 `probe_failed`、`dial_failed`、`manual`）；阶段 B 再扩充。
- 面板按现有 `routeLatencies` 的方式校验：只接受本机已下发的转发和目标，字段限长。

### A.5 前端

- 链路页每条边显示状态标记（正常 / 降级 / 故障，颜色区分），手动的加"手动"标签和到期时间；悬浮显示自动判断结果和原因。
- 边上提供操作菜单：设为正常 / 降级 / 故障、选择时长、备注、恢复自动。
- 服务器列表与服务器详情提供"作为中转"的服务器级操作，列出受影响的链路数。
- 全局网络页的连线按状态着色（如果改动不大；否则留到阶段 B）。

### A.6 告警

Telegram 新增事件 `relayState`（默认开）：

- 手动设置与恢复：发一条，写明操作内容、范围、到期时间。
- 自动判故障与恢复：同一台上一跳的同类变化合并成一条。
- 同一条线路 10 分钟内的反复切换只发第一次，之后合并为"10 分钟内切换 N 次"。

### A.7 测试

- 候选顺序：正常 → 降级 → 自动故障；手动故障不出现；轮询只在正常目标里轮转。
- 强制正常时自动降级不生效；自动故障仍生效，故障后排到可用目标之后，恢复后回到首位。
- 线路级覆盖服务器级；到期后回到自动（面板侧与 Agent 侧各测一次）。
- 让某跳没有可用目标的设置被拒绝；单服务器跳不能设故障。
- 修改 override 不重启规则、不断已有 TCP 连接；UDP 会话按表格迁移。
- 上报校验：伪造的转发 ID、目标、超长字段被丢弃。

## 阶段 B：自动质量判断

全部在上一跳的 `internal/forward` 里完成，按"上一跳 → 目标"独立判断。只影响 `source = auto` 的目标；有手动设置时只记录、不生效。

### B.1 主动信号

现有每 5 秒的探测增加记录建连耗时（丢包时 SYN 重传，耗时会跳到 1 秒以上）。每个目标保留最近 1 分钟（12 次）的结果和过去 1 小时的耗时基线（滑动平均，只用成功样本）。

满足任一条件记为"主动变差"：

- 最近 12 次中失败 ≥ 3 次（但未达到连续 2 次失败的故障条件）；
- 最近 12 次成功耗时的中位数 **同时** 满足：超过自己基线的 3 倍且至少多 100 ms，**并且** 超过同组当前最好目标的 2.5 倍且至少多 50 ms。

同组只有一个目标时不比较同组（反正也没有可切换的）。

### B.2 被动信号

统计真实连接：客户端已经发出数据、但上游在**没有返回任何字节**的情况下**由上游一侧**断开（EOF 或 RST），或建连成功后 `tcpInitialTimeout` 内无下行数据。客户端自己断开的不算。

这个信号可以被人为制造（有人往入口灌垃圾、客户端密码过期后反复重连），所以必须同时满足：

- 按客户端来源 IP 去重：同一来源在 1 分钟窗口内最多计 1 次"坏"、1 次"好"。
- 1 分钟窗口内去重后至少 20 个来源才判断。
- 坏比例 ≥ 50%，**并且** 比同组其他目标的坏比例高出至少 30 个百分点（同组只有一个目标时不判断）。
- **被动信号单独只能触发降级，不能触发故障。**

这个信号用来补"上一跳握手成功、但下一跳后面已经断了"的盲区。

### B.3 状态机

```
正常 ──(主动变差或被动变差 连续 2 个窗口)──▶ 降级
降级 ──(连续 2 分钟两种信号都正常)──▶ 试跑
试跑 ──(试跑期至少 10 个样本且无变差，再持续 2 分钟)──▶ 正常
试跑 ──(任一信号变差)──▶ 降级，下次观察期翻倍（2 → 4 → 8 … 最长 30 分钟）
任意 ──(现有故障条件：连续 2 次探测失败或真实连接建连失败)──▶ 故障
故障 ──(连续 2 次探测成功)──▶ 降级（而不是直接回正常），再走上面的恢复流程
```

- 试跑：每 10 个新连接给它 1 个（轮询模式按计数，主备模式在首选目标处于试跑时同样只给 1/10，其余给下一个正常目标）。
- 进入正常并稳定 1 小时后，翻倍的观察期重置为 2 分钟。
- 降级与试跑都不断开已有 TCP 连接和 UDP 会话；只有进入故障时按现有逻辑迁走 UDP 会话。
- 同组所有目标都被自动降级时，按"都正常"对待（排序沿用配置顺序），避免整体雪崩；仍然上报降级状态。

### B.4 上报与展示

- `relayStates` 的 `autoState` 增加 `degraded`、`probation`（试跑）；`reason` 增加 `slow_handshake`、`probe_loss`、`blackhole`（被动信号）。
- 同时上报最近 1 分钟的统计摘要：探测成功数、耗时中位数、基线、被动坏比例与样本数（数值限范围）。
- 链路页悬浮框显示这些摘要；`relayState` 告警带上原因。

### B.5 不做

- 往代理端口发送测试数据（代理协议会把它当探测攻击处理）。
- 另开回显端口。
- 读取系统内核的连接统计（重传、往返时间）：留作以后的增强。
- 迁移已有连接。
- 入口被攻击时切换入口（客户端直连入口，需要订阅或 DNS 层的方案，另行设计）。

### B.6 测试

用本地回环目标加可控延迟、丢包与"接受后立刻断开"的假上游：

- 握手变慢 → 降级；只有自己慢才降级，大家一起慢不降级。
- 失败 3/12 → 降级；连续 2 次失败 → 故障；故障恢复后先到降级再试跑。
- 黑洞上游（接受后不回数据就断）在来源足够多时降级；来源少于 20、或少数来源刷量时不降级；被动信号不会单独导致故障。
- 试跑分配比例约 1/10；试跑期变差回到降级且观察期翻倍，上限 30 分钟。
- 同组全部降级时按都正常分配。
- 手动设置存在时自动结果只上报不生效。

## 阶段 B 补充：下游不可用的传递与试跑上限

阶段 B 实现后发现两处设计缺陷，在这里补上。

### B2.1 下游不可用的传递（由面板完成）

问题：被动信号要求同一目标 1 分钟内至少 20 个不同来源，且同组有可比较的目标。实际上：

- 中间跳的来源永远是上一台服务器，只有 1 个；
- 主备模式下备用目标平时没有流量，没有可比较的对象；
- 用户少的链路连入口都凑不够 20 个来源。

所以"上一跳握手成功、但下一跳后面已经断了"的盲区在多数部署里仍然存在。

做法：每台中转已经在上报自己到下一跳的状态。面板在收到上报时计算：对某条链路，如果中转 X 在这条链路里的**所有**下一跳目标都处于故障（自动或手动），就认为 X 在这条链路上"下游不可用"。

- 面板把它作为一个**自动来源**的状态下发给 X 的上一跳：`ForwardTarget` 增加 `downstream`（`""` 或 `down`），上一跳把带 `downstream = down` 的目标当作自动故障处理（排在最后兜底），原因 `downstream_down`。
- 它和手动设置的关系与自动故障相同：手动故障、手动降级照常生效；强制正常不屏蔽它（与"自动故障照常生效"一致）。
- 去抖：X 的下游连续 2 次上报都不可用才下发；恢复时 X 的下游有任一目标连续 2 次上报为非故障才撤销。同一条线路 10 分钟内最多下发 6 次变化，超出时保持当前状态并在链路页提示"状态抖动"。
- 只改 `downstream` 时走阶段 A 已有的"原地重载、不重启"路径。
- 上报中的 `reason` 增加 `downstream_down`；链路页与 Telegram 显示"下游不可用"。
- X 是离线管理或 Agent 版本低于 0.6.32（没有上报）时不传递。

### B2.2 试跑上限

问题：试跑晋级要 10 个来自不同来源的成功样本。用户少的链路、或空闲时段，试跑可能一直结束不了，首选中转长期只分到 1/10 的连接。

做法：试跑满 10 分钟后，如果这段时间主动探测全部成功、耗时没有超标、也没有任何被动失败样本，就直接回到正常；有任何变差照旧退回降级。

### B2.3 测试

- 中转 X 的所有下一跳都故障 → 上一跳把 X 排到最后；X 的任一下一跳恢复 → 撤销。去抖与 10 分钟 6 次的限制生效。
- 只改 `downstream` 不重启规则、不断已有连接。
- 低流量下试跑 10 分钟后自动晋级；期间出现一次被动失败则不晋级。
